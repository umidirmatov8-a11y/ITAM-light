# Архитектура ARA

Модульный монолит: один локальный backend-сервис (Node.js/Express) отдаёт API `/api/*` и собранный React-интерфейс.

```
AccessRightsAuditor/
├─ server/
│  ├─ src/
│  │  ├─ rules-core/        # независимый Rule Engine (чистые функции, без БД)
│  │  ├─ modules/
│  │  │  ├─ auth/           # вход, сессии, RBAC, тайм-аут
│  │  │  ├─ admin/          # пользователи, настройки, политика критичности, журнал, резервные копии
│  │  │  ├─ reference-data/ # системы, подразделения, должности, сотрудники, роли, модули, операции, алиасы, импорт справочников
│  │  │  ├─ access-matrix/  # версии матрицы, правила, импорт, утверждение
│  │  │  ├─ imports/        # загрузка файлов, SHA-256, мастер маппинга, нормализация, карантин
│  │  │  ├─ audits/         # запуск, снимок версии правил, находки, комментарии, воспроизводимость
│  │  │  ├─ sod/            # правила SoD
│  │  │  ├─ exceptions/     # журнал исключений
│  │  │  ├─ comparisons/    # сравнение снимков
│  │  │  ├─ reports/        # XLSX (exceljs), PDF (pdfkit + DejaVu Sans)
│  │  │  └─ dashboard/
│  │  ├─ common/            # БД, миграции, разбор XLSX/CSV, журнал действий, CRUD
│  │  └─ cli/               # migrate, create-admin, seed-demo
│  └─ tests/                # тесты Rule Engine (vitest)
├─ web/                     # React + Vite
├─ database/migrations/     # SQL-миграции (применяются при старте)
├─ docs/                    # документация и шаблоны импорта
├─ scripts/                 # install/start/backup для Windows
└─ docker/                  # PostgreSQL для разработки
```

## Поток обработки

1. Аудитор создаёт аудит (дата среза; версия матрицы, действующая на эту дату, подбирается автоматически) и загружает файлы.
2. Импортёр сохраняет оригинал в `data/imports/<audit>/` и вычисляет SHA-256. Файлы с макросами отклоняются, формулы не исполняются.
3. Мастер сопоставления задаёт лист, строку заголовка и колонки. Парсер превращает строки в атомарные назначения: составные ячейки разделяются, роль без операций разворачивается в её состав. Ошибочные строки попадают в карантин (`import_rows`), неоднозначные получают статус `NEEDS_REVIEW`.
4. Нормализатор сопоставляет сотрудника только по табельному номеру или алиасу; системы, роли, модули и операции — по коду, наименованию или алиасу.
5. При запуске аудита фиксируется «версия правил» (`audit_runs.rules_snapshot`): SoD-правила, политика критичности, исключения, кадровые данные сотрудников снимка, состав ролей и риски операций.
6. Rule Engine проверяет каждое назначение, затем выполняет групповые SoD-проверки и связывает находки с исключениями.
7. Результаты и контрольные суммы (пакет, матрица, версия правил, результаты) сохраняются. После этого снимок защищён триггером БД от изменений.

## Классификация (rules-core)

| Код | Тип | Базовая критичность |
|---|---|---|
| ARA-R01 | IDENTITY_UNRESOLVED — сотрудник не найден/неоднозначен | Требует проверки |
| ARA-R02 | UNKNOWN_REFERENCE — неизвестная система/роль/операция | Требует проверки |
| ARA-R03 | TERMINATED_USER_ACCESS — доступ у уволенного | Критическое |
| ARA-R04 | NOT_IN_MATRIX — система/роль не описана в матрице | Требует проверки |
| ARA-R05 | EXPLICITLY_DENIED — явный запрет | Из правила / Высокое |
| ARA-R06 | ROLE_NOT_ALLOWED — роль не разрешена для должности | Высокое |
| ARA-R07 | SCOPE_MISMATCH — роль разрешена должности в другом подразделении | Среднее |
| ARA-R08 | EXCESS_OPERATION — операция сверх состава разрешённой роли | Среднее |
| ARA-R09 | RESIDUAL_AFTER_TRANSFER — права прежней должности после перевода | Среднее |
| SOD-<код> | SOD_CONFLICT / SOD_CONFLICT_COMPENSATED | Из правила / Требует проверки |

Базовая критичность настраивается («Матрица полномочий → Политика критичности»). Эскалация по риску операции (`operations.risk_level`) поднимает критичность до уровня риска операции. Если для находки есть действующее исключение, её результат — «Покрыто исключением», а критичность — «Требует проверки» (исходная критичность сохраняется в `details`). Если исключение истекло, результат — «Исключение истекло» с исходной критичностью.

## Безопасность

* Пароли хранятся как bcrypt (cost 12). Политика паролей: не менее 10 символов, буквы и цифры. Временный пароль нужно сменить при первом входе.
* Сессия — случайный токен в HttpOnly-cookie с `SameSite=Strict`; в БД хранится только SHA-256 токена. Тайм-аут бездействия и максимальная длительность сессии ограничены, после N неудачных входов учётная запись блокируется.
* Изменяющие запросы требуют заголовок `X-ARA-Request` (защита от CSRF). Заголовки безопасности ставит Helmet (CSP).
* `activity_logs` защищён триггером от UPDATE и DELETE. Административные действия помечены категорией `ADMIN`, входы — `AUTH`.
* Утверждённые версии матрицы и снимки выполненных аудитов защищены триггерами БД.
