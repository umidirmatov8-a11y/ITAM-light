# Access Rights Auditor (ARA)

Локальное веб-приложение для аудита банковских полномочий. Оно сверяет фактически назначенные роли и операции с утверждённой матрицей доступа, кадровыми данными, правилами разделения обязанностей (SoD) и журналом исключений.

* **Стек:** Node.js + TypeScript (Express) — локальный сервис/API; React + TypeScript — интерфейс; PostgreSQL — база данных.
* **Анализ:** детерминированный Rule Engine (`server/src/rules-core`), без AI в принятии решений.
* **Импорт / экспорт:** XLSX, CSV → XLSX, PDF.
* **Работа:** только локально. Сервер слушает `127.0.0.1:3000`, интерфейс открывается в браузере.

> По ТЗ клиент предполагался как Electron. По просьбе заказчика сделан как локальное веб-приложение: тот же React-интерфейс открывается в браузере на `http://localhost:3000`. При необходимости его можно обернуть в Electron без изменений сервера.

## Возможности

| Раздел ТЗ | Реализация |
|---|---|
| 2. Роли приложения | Системный администратор, Администратор матрицы, Аудитор ИБ, Владелец системы (видит только свои системы, может подтвердить/оспорить), Наблюдатель. RBAC на сервере, журнал действий. |
| 3.1 Справочники и матрица | Системы, подразделения, должности, сотрудники, роли, модули, атомарные операции, состав ролей, алиасы. Версии матрицы: черновик → утверждена → архив. Утверждённую версию изменить нельзя (защищено триггером БД), её можно только склонировать. Импорт правил из XLSX/CSV. |
| 3.2 Импорт | Несколько файлов в пакете аудита. Мастер сопоставления колонок с автоподбором и сохраняемыми шаблонами. Сохраняются оригинал файла, SHA-256, автор и параметры маппинга. Проверки: пустые поля, дубли, неизвестные значения, некорректные даты, неоднозначные ID. Ошибочные строки попадают в карантин и не прерывают импорт. Составные ячейки и профили ролей раскладываются на атомарные права. Макросы отклоняются, формулы не исполняются. |
| 3.3 Rule Engine | Роль не разрешена; избыточная операция внутри разрешённой роли (отдельно от лишней роли); несоответствие области действия; явный запрет; доступ уволенного; остаточный доступ после перевода; назначение вне матрицы («Требует проверки», а не нарушение). Для каждой находки есть код правила, объяснение, ожидаемое и фактическое право. |
| 3.4 SoD | Конфликты на уровне операций и ролей, 2 и более сторон. Область проверки: сотрудник целиком или сотрудник в пределах одной системы. Жёсткий конфликт отличается от конфликта с утверждённым компенсирующим контролем. Показываются обе стороны и исходные назначения. |
| 3.5 Исключения | Обязательные поля из ТЗ. Исключение не снимает находку, а помечает её «Покрыто исключением»; истёкшие исключения выявляются при каждом запуске. Исключения не удаляются, только отзываются. |
| 3.6 История | Каждый аудит — неизменяемый снимок (файлы, записи, версия матрицы, версия правил, результаты, контрольные суммы). Есть кнопка «Проверить воспроизводимость». Снимки сравниваются по стабильному ключу; результат: ADDED / REMOVED / CHANGED / NEW_FINDING / RESOLVED / PERSISTING и отдельный список неоднозначных записей. |
| 3.7 Отчёты | XLSX: сводка, все назначения, нарушения, SoD, исключения, ошибки импорта, изменения. PDF: титул, параметры, показатели, критические находки, методология, ограничения. Фильтры: система, подразделение, должность, критичность, тип, результат, владелец, статус. |
| 10. ИБ | bcrypt (cost 12), блокировка после неудачных входов, тайм-аут бездействия, журнал входов, неизменяемый журнал действий (триггер), защита от CSRF, CSP, сервер только на localhost, TLS к PostgreSQL через `PGSSLMODE`, резервное копирование. |
| 11. НФТ | 100 000 атомарных назначений: импорт ≈ 8 с, анализ ≈ 10 с (тестовый стенд). Повторный запуск даёт идентичную контрольную сумму результатов. |

## Требования

* Windows 10/11 (работает и на Linux/macOS).
* **Node.js 20.19+ или 22 LTS** — https://nodejs.org
* **PostgreSQL 14+** (проверено на 16) — локально или на сервере банка.

## Установка (Windows)

1. Установите PostgreSQL и создайте базу и пользователя (через `psql` или pgAdmin):
   ```sql
   CREATE USER ara WITH PASSWORD 'надёжный_пароль';
   CREATE DATABASE ara OWNER ara;
   ```
   Альтернатива для разработки — `docker compose -f docker/docker-compose.yml up -d`.
2. Скопируйте `.env.example` в `.env` и укажите параметры подключения (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`).
3. Запустите `scripts\install.bat`. Скрипт установит зависимости, соберёт интерфейс и сервер и применит миграции.
4. Запустите `scripts\start.bat` и откройте http://localhost:3000.

При первом запуске создаётся пользователь `admin`. Временный пароль выводится в консоль один раз, при первом входе его нужно сменить. Можно задать пароль заранее через `ARA_ADMIN_PASSWORD` в `.env`. Если пароль потерян:

```bash
npm run create-admin -- admin
```

Те же шаги из командной строки:

```bash
npm ci
npm run build
npm start
```

### Демонстрационные данные

```bash
npm run seed:demo
```

Скрипт создаёт две системы (Smart Bank, NCI), 11 сотрудников, утверждённую матрицу, три SoD-правила, два исключения (действующее и истёкшее) и два выполненных аудита со сравнением. Ещё он создаёт демо-пользователей `auditor`, `matrix`, `owner_sb`, `owner_nci`, `viewer`; их пароль выводится в консоль или задаётся через `ARA_DEMO_PASSWORD`. Примеры выгрузок и шаблоны импорта лежат в `docs/import-templates/`.

## Порядок работы

1. **Оргструктура и кадры** — импортируйте кадровый справочник (`hr_employees.csv`).
2. **Системы и операции** — импортируйте каталог ролей и операций (`catalog_roles_operations.csv`), задайте владельцев систем.
3. **Матрица полномочий** — создайте версию, импортируйте или введите правила (`matrix_rules.csv`), затем утвердите.
4. **SoD-правила** и **Исключения** — заведите конфликты и согласованные исключения.
5. **Аудиты и импорт** — создайте аудит на дату среза, загрузите выгрузки, сопоставьте колонки и запустите аудит.
6. Разберите находки (комментарии, статусы), выгрузите отчёты XLSX/PDF и сравните аудит с предыдущим в разделе «История».

## Конфигурация (`.env`)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` | localhost, 5432, ara, ara | Подключение к PostgreSQL (или `DATABASE_URL`) |
| `PGSSLMODE` | — | `require` / `verify-full` — TLS, если БД на другом хосте |
| `ARA_HOST`, `ARA_PORT` | 127.0.0.1, 3000 | Адрес сервера. Не открывайте его в сеть без TLS-прокси |
| `ARA_DATA_DIR` | `data` | Оригиналы импортов, отчёты, резервные копии. Ограничьте доступ к каталогу |
| `ARA_PG_DUMP` | `pg_dump` | Путь к pg_dump для резервного копирования из интерфейса |
| `ARA_ADMIN_USERNAME`, `ARA_ADMIN_PASSWORD` | admin, случайный | Первый администратор |
| `ARA_SECURE_COOKIES` | false | `true`, если приложение открыто через HTTPS |

Тайм-аут сессии, блокировку входа и лимит размера файла администратор меняет в интерфейсе: «Пользователи и настройки → Параметры».

## Резервное копирование и восстановление

* Из интерфейса: «Пользователи и настройки → Резервное копирование». Создаётся дамп БД и копия файлового хранилища в `data/backups/<дата>`.
* Скриптом: `scripts\backup.ps1`.
* Восстановление:

  ```bash
  pg_restore --clean --no-owner -d ara data/backups/<дата>/ara-db.dump
  ```

  Затем скопируйте каталоги `imports` и `reports` из резервной копии обратно в `data/`.

## Разработка

```bash
npm run dev
```

Запускает сервер с автоперезапуском (порт из `.env`). Интерфейс с горячей перезагрузкой — в отдельном терминале:

```bash
npm run dev:web
```

Он доступен на http://127.0.0.1:5173 и проксирует `/api` на сервер.

Модульные тесты Rule Engine:

```bash
npm test
```

Структура проекта описана в [`docs/architecture.md`](docs/architecture.md), модель данных — в [`docs/data-dictionary.md`](docs/data-dictionary.md).

## Ограничения MVP

* Данные поступают только через файлы. Прямого подключения к банковским системам, AD или IAM нет, доступы в целевых системах приложение не изменяет.
* Проверка SoD в масштабе подразделения или процесса (а не одного сотрудника) не реализована.
* Интерфейс на русском языке. Подписи вынесены в `web/src/i18n.ts`, чтобы можно было добавить узбекский.
